# WPE WebKit под OpenHarmony (x86_64, musl)

Перекрёстная сборка обозревательного движка WPE WebKit 2.54.0 для OpenHarmony
7.0, работающего на обычном Linux x86_64 без init, где службы запускает
`arkvm/start.sh`.

Собираем в контейнере, ставим и запускаем на хозяйской машине.

---

## Быстрый ход

```sh
# на хозяйской машине, из /mnt/ohos/wpe
./wpe.sh build      # образ + все зависимости  (примерно 40 минут)
./wpe.sh engine     # сам движок               (примерно 1,5 часа)
```

Отдельные действия:

```sh
./wpe.sh image      # только пересобрать образ контейнера
./wpe.sh deps       # только зависимости
./wpe.sh shell      # войти в контейнер руками
```

Сборка пошаговая: каждая готовая библиотека отмечается в `out/.stamps`.
Повторный запуск продолжает с места остановки. Пересобрать одну:

```sh
rm /mnt/ohos/wpe/out/.stamps/glib && ./wpe.sh deps
```

## Почему не родной компилятор OpenHarmony

В пакете OpenHarmony лежит clang 15 и его стандартная библиотека той же
версии. WebKit 2.54 написан на C++23 и требует:

* `std::expected` — появился в libc++ 16;
* `std::ranges::count`, `reverse`, `lower_bound`, `fill`, `std::views::transform`
  — в пятнадцатой версии их нет или они неполны;
* послабление C++20, разрешающее опускать `typename` перед зависимыми типами, —
  clang 15 его не реализует.

Поэтому берём clang 18 из Ubuntu. Он уже знает цель `x86_64-linux-ohos`
(поддержка OpenHarmony принята в LLVM с 17-й версии), так что компилятор
собирать не приходится — только стандартную библиотеку C++.

Три мелочи, которые для этого понадобились:

1. **Пустые `crtbeginS.o` / `crtendS.o`.** Штатный clang их ожидает, в
   OpenHarmony их нет: musl запускает начальные действия через `.init_array`,
   и содержать этим файлам нечего.
2. **Подставной каталог времени исполнения** (`clang18-rt`): заголовки от
   clang 18, а `libclang_rt.builtins.a` — из пакета OpenHarmony. Она написана
   на C и совместима между версиями.
3. **`libc++`, `libc++abi`, `libunwind` 18-й версии**, собранные тем же clang 18
   под OpenHarmony. Делаются разделяемыми: если вшить их в каждую библиотеку
   движка и в каждый его процесс, описания типов задвоятся.

## Подкладка под заголовки

В пакете OpenHarmony заголовки ядра взяты из набора для Android. Там
`linux/socket.h` объявляет `sockaddr_storage`, который musl уже объявил в
`sys/socket.h`. Любой исходник, включающий оба, не собирается — это задевает
glib, libsoup и сам WebKit.

Лечится одной подкладкой `shim/linux/socket.h`: она отдаёт только то, чего в
musl нет (`_K_SS_MAXSIZE`, `__kernel_sa_family_t`), а саму структуру берёт
оттуда. Каталог `shim` стоит в поиске раньше корня заголовков.

## Что берём из системы, а не собираем

| Что | Откуда | Примечание |
|---|---|---|
| **zlib** | пакет OpenHarmony | есть и заголовок, и библиотека |
| **EGL, GLES2/3** | пакет OpenHarmony | |
| **native_window, native_buffer, native_vsync, native_fence** | пакет OpenHarmony | понадобятся для площадки вывода |

### Почему ICU всё-таки свой

На устройстве `/system/lib64/libicu.so` — это не сам ICU, а тонкий переходник
(121 КБ), выставляющий наружу 1110 вызовов настоящих `libhmicuuc.z.so` и
`libhmicui18n.z.so`. Заманчиво было переиспользовать его и сэкономить
тридцать пять мегабайт.

Не вышло: переходник выставляет наружу не весь ICU. Нет языковых соглашений
(`udtitvfmt_*`, `ureldatefmt_*`, `ucfpos_*`, `ufmtval_*`, `udatpg_get`) —
это объект `Intl` в JavaScript и форматирование дат. Нет приведения регистра
с учётом языка (`ucasemap_*`), поиска по тексту (`usearch_*`), денежных
единиц (`ucurr_*`). WebKit всё это использует.

Поэтому собираем свой, версии 74.2 — ровно той, что в дереве OpenHarmony,
чтобы поведение совпадало с остальной системой.

ICU собирается в два захода: сперва её собственные средства для машины
сборки, потом сама библиотека под цель. Иначе никак — ICU порождает часть
своих таблиц своими же средствами.

## Что не входит в сборку движка

Выключено намеренно. Каждое отключение либо убирает тяжёлую зависимость,
либо касается того, что на OpenHarmony устроено своими средствами.

| Что | Почему |
|---|---|
| **Звук и видео целиком** | убирает GStreamer — самую тяжёлую зависимость из всех. Воспроизведение будем приделывать через средства OpenHarmony |
| **WebRTC, захват с камеры и микрофона** | то же |
| **Площадки DRM и Wayland** | выводим через поверхность OpenHarmony; следом отпадают libdrm, gbm, libinput, udev, wayland |
| **Отдельный процесс отрисовки** | опирается на gbm |
| **Прежний способ вывода (libwpe)** | отдельный слой, на OpenHarmony не нужен |
| **XSLT** | почти вымерший способ преобразования разметки; тянет libxslt |
| **JPEG-XL, AVIF, управление цветом** | три библиотеки ради редких форматов |
| **WOFF2** | ещё один вид сжатия шрифтов; обычных WOFF хватает |
| **Переносы слов** | требуют libhyphen и словарей на каждый язык |
| **Проверка правописания** | требует enchant со словарями |
| **Речевой вывод** | требует flite или spiel |
| **Доступность (ATK)** | в OpenHarmony свой способ связи с чтецами экрана |
| **Песочница на bubblewrap** | опирается на возможности ядра и отдельную утилиту; в OpenHarmony разграничение своё |
| **Игровые устройства, WebDriver, пробный обозреватель, описания для чужих языков, справка** | не нужны на этом этапе |

Всё это добавляется позже по одному, когда будет что показывать.

## Что дальше

1. **Площадка вывода.** Написать `WPEDisplayOHOS` и `WPEViewOHOS` поверх
   `OHNativeWindow` от `XComponent`. Опора: в движке уже есть `WPEBufferAndroid`
   поверх `AHardwareBuffer`, а `OH_NativeBuffer` в OpenHarmony устроен почти так
   же; к тому же в пакете есть `EGL_OHOS_image_native_buffer`, позволяющий
   сделать `EGLImage` прямо из буфера. Для сравнения: безэкранная площадка
   занимает 452 строки, площадка DRM — 2857.
2. **Раскладка на устройство.** Библиотеки в `/system/lib64`, настройки
   шрифтов из `stage/fontconfig/system/etc/fonts`, вспомогательные процессы
   движка в `/system/libexec`.
3. **Приложение-обозреватель** на ArkTS поверх `XComponent`.
